# 05 · 原生菜单接入

## 症状

想复用侧栏那套行内菜单（置顶 / 重命名 / 分支 / 复制 ID / 归档），自建菜单维护成本高，
且权限门控、快捷键、取消归档永远追不上官方。

## 根因与做法

0.2.2-rc.1 起宿主提供 `contextMenus` 服务。正确做法是**不自绘菜单**，只把目标和视口坐标交给它：

- 会话目标：`{ kind: 'session', value: { sessionId, displayTitle } }`；
- 工作区目标：`{ kind: 'workspace', value: { workspaceId, path, displayTitle } }`；
- 坐标：触发按钮的 `left` / `bottom`（与官方侧栏的 `openSessionMenu` 相同）；
- 打开前先 `focus` 触发按钮；同目标再次打开由宿主按「4px 内」判 toggle；
- 我们的下拉全部关闭时显式 `close()`。

## 证据

- 自建菜单删掉后：权限门控、快捷键键帽、官方重命名/删除对话框、复制 ID 的「已复制」提示、
  取消归档全部免费获得；
- 0.2.1 及更早没有该服务：面包屑与下拉照常，只是行尾没有「⋯」。

## 已知边界（第三方降级实现）

第三方插件可能不走 `contextMenus.register`，而是往**原生侧栏菜单的 DOM** 里注入按钮
（例如 Archive Manager 1.2.7 的降级路径，它要求点击目标有 `data-row-key="workspace:…"`）。
这种条目只出现在侧栏菜单里，不会出现在走服务的自绘下拉里 —— 这不是本插件漏画，而是
对方的集成方式只对宿主 DOM 生效。判断方法：同一项在侧栏有、在顶栏没有，且它的 provider
在服务里查不到。

## 结论

- 「能用原生就不自绘」；插件只负责触发与坐标；
- 不为了对齐第三方的 DOM 注入而给自己加 `data-row-key` 垫片（脆、且要承担注入时序）；
- 老内核的降级是刻意的：不保留第二套菜单。
